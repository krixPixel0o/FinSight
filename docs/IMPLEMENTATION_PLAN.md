# FinSight audit and implementation plan

## Repository audit

FinSight is an existing Spring Boot 4.1.1 / Java 25 / Maven API and React/Vite SPA backed by PostgreSQL. It already has JWT auth, user-scoped account/category/transaction/budget APIs, reports, dashboard aggregation, and basic financial math. Preserve these paths and APIs where practical.

### Findings from the current code

- PostgreSQL is configured, but the README and test database settings were stale MySQL-era configuration.
- The schema was managed by Hibernate `ddl-auto=update`. Read-only inspection of the configured local database found a `flyway_schema_history` table with a recorded V1 users migration, plus legacy columns (`first_name`, `last_name`, `timezone`, timestamps) on `users`; the Flyway V1 script is absent from this checkout. The production path now uses a separate Liquibase history and only baselines existing tables or creates missing tables, leaving the legacy Flyway metadata untouched. Production rollout still requires a database backup and a PostgreSQL migration run before enabling `ddl-auto=validate`.
- The checked-in application config contained a predictable JWT secret. JWT now comes from the ignored local `.env`; no production profile or migration strategy exists yet.
- Security is stateless JWT with public register/login/health and authenticated remaining routes. CORS is restricted to the local Vite origin. An unused Boot-generated in-memory security user was being initialized and has been disabled.
- Financial records use `BigDecimal`; transactions and accounts check ownership in service methods. Transfers are represented as one transaction with source and target accounts. Existing dashboard work excludes future-dated entries and rejects mixed-currency totals.
- Current products are accounts, categories, transactions, budgets, CSV reports, dashboard, and rule-based insights. There are no goals, recurring transactions, investments/debt ledgers, health score, anomaly model, forecast/scenario engine, or Gemini client/assistant.
- Existing tests cover app startup, account ownership, financial math, and dashboard date/currency behavior. They do not yet cover the full HTTP/JWT contract, transaction invariants, budgets, or frontend behavior.
- Account balance responses currently derive balances from transaction history in application code; this can load all of a user's transactions for each account and should be replaced by bounded aggregate queries as volume grows.

## Staged plan

1. **Audit and stabilize:** align docs/config/tests with PostgreSQL, require secrets outside source, capture current API/data invariants, and establish repeatable verification. (Audit and initial config cleanup complete.)
2. **Security and API contracts:** verify JWT/authentication behavior, validation, user isolation, error handling, CORS configuration, and HTTP-level tests. (Service-level ownership and HTTP-level authentication plus goals/liabilities/transactions/budgets isolation coverage are in place. CORS now accepts only exact HTTP(S) origins, exposes only required headers, and disables credentials for bearer-token auth. JWT parsing rejects oversized authorization headers before token parsing. Account endpoint isolation and distributed authentication abuse controls remain.)
3. **Financial engineering foundation:** centralize money/date/currency rules and use grouped balance aggregates. (Grouped balances, Liquibase changelog, clean-schema migration test, PostgreSQL baseline on `finsight2`, additive goal/liability migrations, production Hibernate validation, and HTTP health check are verified.)
4. **Financial health score:** transparent, deterministic, explainable components with insufficient-data handling. (Backend API and UI include savings, expense trend, cash flow, budgets, liquid reserves, manually entered liability payment burden, and manually entered goal progress; missing data remains excluded and disclosed.)
5. **Anomaly detection:** rule/statistical detection grounded in transaction history, with evidence and confidence. (Initial user-scoped category baseline endpoint and Insights display implemented; next review needs more edge cases and performance limits.)
6. **Forecasts and scenarios:** deterministic methods with disclosed assumptions and coverage limits. (Six-completed-month average forecast, uncertainty label, budget runway estimates, planned-contribution goal completion estimates, three deterministic scenario types, and Insights UI implemented; estimates are separate per goal and do not prove affordability.)
7. **Recommendations:** actionable, rule-based advice with evidence and no unsupported financial claims. (Implemented with completed-month comparisons, active budgets, and user-scoped integration coverage.)
8. **Backend Gemini integration:** verify current official API, optional backend-only credentials, bounded timeouts, privacy controls, and graceful disabled/error behavior. (Optional `generateContent` client implemented; bounded timeout, redacted read-only context, no logging/persistence, and disabled path covered. A live provider call still requires a backend-configured API key.)
9. **Approved tool calls:** strict allowlist of read-only user-scoped finance queries; schema validation and no arbitrary SQL or transaction actions. (Assistant context only calls fixed health/forecast/recommendation/anomaly services scoped by authenticated identity.)
10. **Assistant service/API:** ground responses in approved tools and deterministic outputs, validate claims, and persist only what is needed. (Stateless grounded endpoint and request limits implemented; conversation persistence intentionally omitted.)
11. **AI dashboard/UI:** integrate insights, assistant, and financial views into existing React navigation without breaking current screens. (Recommendations and consent-gated assistant panel integrated; frontend production build passes.)
12. **Release hardening:** full regression/security review, query performance, setup docs, environment separation, and acceptance review. (37 backend tests pass; frontend production build and whitespace checks pass; production PostgreSQL profile validates and serves health. Focused coverage verifies planning, transaction, and budget record isolation, unauthenticated access, CORS validation, and JWT tampering. Remaining: account HTTP isolation and distributed auth abuse controls, AI-provider contract testing when a key is available, and verification across every supported legacy schema.)

Each stage should compile, run the relevant backend tests and frontend build, fix regressions, and verify existing functionality before proceeding. The project is not complete until the requested acceptance criteria are verified; successful compilation alone is insufficient.
